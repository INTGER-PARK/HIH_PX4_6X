# Palletrone 4-DoF Admittance Implementation

## Repository audit and insertion point

The authoritative firmware repository is `~/HIH_PX4_6X` (branch `main`, starting commit `c28f02f1`); `~/HIH_PX4` was not modified. The supplied CM4 archive expands to `~/PX4-RPi-CM4-XC330-Palletrone` and contains no Git metadata. Existing user modifications were preserved.

The current observer is `src/modules/palletrone_mob/PalletroneMob.*`; its `PalletroneMobStatus` reports `timestamp_sample`, `FRAME_BODY_FRD`, `force_valid`, `torque_valid`, `warmup_complete`, and modeled-CoM `external_force[3]`/`external_torque[3]`. The observer remains publish-only and its equations, geometry, gains, and signs were not changed.

The custom cascade owner is `MulticopterPositionControl`. Nominal local x/y/z/yaw is assembled into `pose_setpoint`; ROS feed-forward is `custom_command_velocity`; `_control.setInputSetpoint()` and `_control.setVelocityFeedforward()` feed `PositionControl`, where position and velocity errors are evaluated before the unchanged attitude/rate/allocator chain. The admittance reference manager is inserted exactly between nominal reference assembly and those two setters. It is therefore the only effective-setpoint writer and does not publish a competing trajectory setpoint. Existing controller integrators are not reset on admittance transitions.

The compatible activation mode is `custom_mode_flag && flag_control_position_enabled`; arming is `vehicle_control_mode.flag_armed`. A `trajectory_flag` false-to-true edge is the explicit new normal-command session that releases a latched post-admittance hold. Periodic stale position messages cannot release it.

Vehicle attitude uses PX4 `vehicle_attitude.q` and `Dcmf`, producing body-to-local NED rotation. Recorder entry point is `cf_bag/src/bag.cpp`. DDS mapping is `src/modules/uxrce_dds_client/dds_topics.yaml`; ROS messages are generated by the glob in `px4_msgs/CMakeLists.txt`.

The existing controller exposes position/velocity and yaw/yaw-rate feed-forward at this insertion point; admittance acceleration is retained in status and limiting but is not added as cascade acceleration feed-forward.

## Dynamics, frames, and signs

At the modeled CoM/body origin, `q=[dx,dy,dz,dpsi]`, and each axis obeys `M ddq + D dq + K q = u`, with virtual (not physical vehicle) `M>0`, `D>0`, `K>=0`. The core uses variable-dt bilinear/Tustin integration `(I-hA)x[k+1]=(I+hA)x[k]+dt Bu`, not forward Euler, and commits all four axes only after every calculation is finite and valid.

MOB publishes both its raw residual and `corrected=raw-PMOB_BIAS_*`. Admittance consumes only the corrected BODY_FRD wrench: `N_hat=max(0,-Fx_corrected)` and `u_x=deadzone(N_des-N_hat,PADM_N_EDB)`. Y/Z/yaw use corrected `Fy`, `Fz`, and CoM `Tz` with continuous deadzones and native FRD signs. Admittance has no bias subtraction, automatic tare, or contact search.

For K=0 a constant input tends to `dq=u/D` and position continues; after removal damping stops velocity at the new position. For K>0, constant input tends to `q=u/K`. Body velocity is rotated to local NED and integrated as a local offset. This is a small-motion/quasi-static body-aligned model, not full SE(3) spatial admittance.

For ideal y/z/yaw axes, `V=1/2 dq^T M dq + 1/2 q^T K q` and `Vdot=dq^T u-dq^T D dq`, so positive M/D and nonnegative K give passive ideal wrench-to-velocity dynamics. This does not prove closed-loop passivity, and the x desired-force source can inject energy.

## State machine and bumpless ownership

States are `DISABLED_HOLD`, `WAIT_VALID`, `WAIT_CONTACT`, `BLEND_IN`, `ACTIVE`, `HANDOVER_DECEL`, and `FAULT_HOLD`. ON is only a request. Master enable, fresh locally-timed heartbeat, compatible mode, optional arming, finite attitude, fresh BODY_FRD/warm MOB, force validity, optional yaw torque validity, valid parameters, and contact dwell are required. Contact uses `N_ON/N_OFF` hysteresis and dwell/grace times.

On entry, the current finite effective pose is latched as base and all offsets/states start at zero, so the position/yaw setpoint does not jump. OFF, timeout, invalidity, or sustained contact loss enters damping-only handover with zero new wrench and K ignored. Velocity continues to feed the unchanged cascade while the pose remains integrated. At the stop thresholds or timeout, the current effective pose is atomically copied to base before offsets are cleared: `base_new=base_old+offset`, hence `effective_after=effective_before`. The old nominal target is never restored. Severe nonfinite faults latch the last finite effective pose and zero feed-forward in `FAULT_HOLD`.

Input, acceleration, velocity/rate, and position/yaw offsets are limited per axis. At an offset boundary outward state is stopped while inward return remains possible; flags expose every saturation.

## ROS 2 command, status, and logging

`palletrone_admittance_keyboard` starts OFF, reads `a/x/r/q` immediately through RAII termios plus nonblocking `poll`, publishes reliable keep-last-1 volatile heartbeats at 10 Hz, and displays actual PX4 status at 2.5 Hz. Reset counters are edge-triggered and reset is refused during ACTIVE/HANDOVER. Quit, EOF, SIGINT, SIGTERM, and SIGHUP publish best-effort OFF and restore the terminal. It never changes `PADM_EN` and is not in flight launch files.

Command: `/fmu/in/palletrone_admittance_command`. Status: `/fmu/out/palletrone_admittance_status`. The bag recorder independently records these plus MOB and the unchanged legacy `/data_logging_msg`; its 92-field schema was not edited.

## Parameters and initial values

General defaults: `PADM_EN=0`, `ARM_ONLY=1`, `CMD_TO=.5 s`, `MOB_TO=.1 s`, `IN_T=.25 s`. Contact: `N_DES=2 N`, `N_ON=.8 N`, `N_OFF=.4 N`, with configurable dwell/deadband. Axis defaults are X `(M,D,K)=(4,40,0)`, Y/Z `(6,60,0)`, yaw `(J,D,K)=(.2,1,0)`. Velocity limits are `.05/.15/.15 m/s` and `.30 rad/s`; offset limits `.10/.30/.30 m` and `.35 rad`. Handover defaults are `1.5 s`, `.01 m/s`, `.02 rad/s`, damping scale `1.5`. Deadband, input, acceleration, velocity, and position limits remain runtime PADM parameters; the former PADM bias parameters were removed because bias now belongs to MOB.

## Runtime procedure

PX4 NSH (only after normal hardware safety preparation):

```
palletrone_mob start
param set PMOB_EN 1
param set PADM_EN 1
param show PADM_*
listener palletrone_mob_status 10
listener palletrone_admittance_command 10
listener palletrone_admittance_status 10
```

CM4 separate SSH terminal:

```
source /opt/ros/humble/setup.bash
source ~/PX4-RPi-CM4-XC330-Palletrone/install_admittance/setup.bash
ros2 run px4_ros_com palletrone_admittance_keyboard
ros2 topic info /fmu/in/palletrone_admittance_command -v
ros2 topic echo /fmu/out/palletrone_admittance_status
ros2 topic hz /fmu/out/palletrone_admittance_status
```

Keys: `a` request toggle, `x` OFF, `r` inactive reset, `q` OFF and quit.

## Safety and limitations

MOB is a model-based lumped residual, not ground-truth contact wrench; mass/inertia/CoM/thrust/servo/EKF errors enter it. No CoP/contact point or surface-centre wrench shift is estimated. CoM Tz may include tangential-force lever-arm torque. Delay/noise, sampling, cascade and actuator dynamics, saturation, and environment stiffness prevent an automatic whole-system passivity/stability claim. There is no direct motor/wrench compensation, automatic contact search, hardware flashing, arming, motor, servo, or propeller test in this work.

Build and exact verification results are recorded in the final task response after execution.
